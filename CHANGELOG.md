# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Fixed

- The verification after a node restart: the identity check tells a refused credential (Access is denied, 0x80070005, HTTP 401) from a node that did not answer (timeout, connection reset or closed, restarting) and retries the latter; the run waits for a node it restarted (port, then session, run setting `restartWaitMinutes`, default 15) before the final verify, with a `NodeWaiting` heartbeat and an honest 'did not come back within N minutes'; a driver install that returns pnputil 3010 is recorded as restart required and the node is restarted once, at the end of the apply.

### Changed

- Defender for Cloud: new optional key `security.defender_for_cloud.security_contact_email` (registry 5.0.32, infrastructure schema 5.6.8). `Enable-DefenderForCloud.ps1` sets it as the security contact of the subscription when there is none. Free.
- Moved four groups of tasks out of the route into `scripts/deferred` (see its README): Windows Admin Center (three task folders), backup and disaster recovery (the stage 05 phase and the stage 06 validation), PIM and conditional access, and the network device syslog collector. Nothing runs them; they are no longer in the task catalogue, and `Invoke-PostTerraformConfiguration.ps1` no longer offers the `wac-server` and `syslog-receiver` roles.

- Removed the Datadog task (stage 05, monitoring task 07: three scripts) and the old-layout Datadog keys (registry 5.0.31). The toolkit installs no third-party agent. Nothing called the task.
- Removed the per-machine Azure Update Manager task (stage 05, security task 05: three scripts). It set patch assessment, the patch extension and a maintenance configuration on the machines one by one, which Microsoft does not support for Azure Local machines; the instance is updated as a whole.
- Terraform: the `monitoring` module no longer adds the legacy `Updates` and `Security` Log Analytics solutions.

- Log Analytics workspace (stage 05, monitoring task 01): `Deploy-MonitoringSecurity.ps1` is replaced by `Deploy-LogAnalyticsWorkspace.ps1`. It creates the one workspace of `operations.monitoring` from the master `infrastructure.yml` and nothing else. The old script also created a second workspace for Microsoft Sentinel in a security subscription and three data collection rules with fixed names, read a configuration layout that no longer exists and could not run. Nothing in the automation is for Microsoft Sentinel. Its parameters are registered (registry 5.0.30).
- Terraform: the `security` module no longer has a Defender for Cloud pricing resource, and the `defender_plans` variable and the `defender_plan_ids` output are removed. The automation cannot turn on a paid plan.
- Defender for Cloud: the automation turns on only the free level Azure Local needs (Foundational CSPM and the Microsoft cloud security benchmark assignment), from the new keys `security.defender_for_cloud.enabled` and `apply_cloud_security_benchmark` (registry 5.0.29, infrastructure schema 5.6.7). `Enable-DefenderForCloud.ps1` no longer turns on Defender for Servers, Storage, Key Vault or Resource Manager, nor agent auto-provisioning. The Terraform `defender_plans` default is empty. `Test-SecurityCompliance.ps1` checks the free level, not paid plans. The script that turns on paid plans moved to `scripts/optional/paid-security-services` and is run by nothing.

- Variables: `storage.configuration_mode` and `storage.volumes` now apply to S2D clusters as well. The condition "san or hybrid" sat on the whole `storage` section and removed it from the S2D scenario template; it now limits only `storage.san`. Registry 5.0.28.
- Variables: every variable script and document is under `config/variables`. `New-InfrastructureVariablesReference.ps1` (from `scripts/common/infrastructure`) and `Test-VariableConfig.ps1` (from `scripts/tools/qa`) are in `config/variables/scripts`; `variables-audit-tasks.md` and the variable flow diagram are in `config/variables/docs`. Removed, nothing called them: `CanonicalVariable.psm1`, `registry-variable.ps1` (`scripts/common/utilities/helpers`) and `canonical_variables.py`.
- Removed `config/infrastructure` (the generated stub copies of the schema and of the two example files, and the pointer pages). `config/variables` is the only place for the master registry, the schemas, the templates, the examples and the variable documents; azurelocal-ztp, azurelocal-sonar and Trailwright read `config/variables/schema/infrastructure.schema.json` and `config/variables/examples/`.
- The node-configuration scripts and modules build local paths per segment (`Join-Path`, `[IO.Path]::Combine`), so they run under `pwsh` on a Linux runner as well as Windows; `tests/node-configuration/CrossPlatform.Tests.ps1` scans them for backslash path literals. Paths on the nodes (`C:\SBE`) stay Windows paths.
- The step order of the one-run OS configuration is the order the node script runs them in, with `Sbe` last (the SBE package is the step most likely to fail and must not stop the others).- Removed the staging storage account for the SBE package: `Set-AzureLocalNodeConfiguration.ps1 -StagingStorageAccount` and `-StagingContainer`, `New-AzlArcRunCommandTransport -StagingStorageAccount`/`-StagingContainer`, the blob upload and read-only SAS path, the `sas:<name>` secret, and the Az.Storage and Storage Blob roles it needed. Azure Arc Run Command can't carry a file; use `hardware.sbe.delivery`.
- Removed the staging storage account for the SBE package: `Set-AzureLocalNodeConfiguration.ps1 -StagingStorageAccount` and `-StagingContainer`, `New-AzlArcRunCommandTransport -StagingStorageAccount`/`-StagingContainer`, the blob upload and read-only SAS path, the `sas:<name>` secret, and the Az.Storage and Storage Blob roles it needed. Azure Arc Run Command can't carry a file; use `hardware.sbe.delivery`.
- Removed the MkDocs site, docs publishing workflow, and repository `docs/` tree; the README is now the primary repo-level documentation.

### Features

- Alerting action group (phase 02 monitoring and observability, task 04, `Deploy-ActionGroup.ps1`; second half of the monitoring deployment): creates the action group `operations.monitoring.action_group` with an email receiver for each address of `operations.notifications.emails` and `operations.monitoring.alert_email`; an existing group keeps its receivers and gains the missing addresses. New infrastructure.yml key `operations.monitoring.action_group` (registry 5.0.27, infrastructure schema 5.6.6). The descriptions of the monitoring and notification keys and of `identity.entra.groups` no longer say "not read by the tools yet".
- Data collection endpoint (phase 02 monitoring and observability, task 01, `Deploy-DataCollectionEndpoint.ps1`; first half of the monitoring deployment): creates the endpoint `operations.monitoring.data_collection_endpoint` in the resource group and the region of the Log Analytics workspace it feeds, once the workspace exists; does nothing when `operations.monitoring.enabled` is false. An existing endpoint is left alone. Registry 5.0.26 registers its parameters; no new infrastructure.yml key.
- Key Vaults (phase 04 manual deployment, task 10, `Deploy-KeyVaults.ps1`): creates each `key_vaults[]` entry (Standard, Azure RBAC, soft delete; purge protection unless `scenario.environment_class` is lab, test or dev) and lists which secrets the `keyvault://` references of the file still lack. It never writes or asks for a secret value. Registry 5.0.25 registers its parameters; no new infrastructure.yml key.
- Virtual networks (phase 04 manual deployment, task 01, `Deploy-VirtualNetworks.ps1`): creates each `landing_zone.networks[]` entry with its address space, DNS servers and subnets in the subscription and resource group it names, and peers the networks that list each other in `peer_with`, in both directions. Additive and safe to repeat: a missing subnet is added, a security group or route table is attached once it exists, anything else that differs is reported and left alone, nothing is removed. Registry 5.0.24 registers its parameters; no new infrastructure.yml key.
- Automation managed identity (phase 03 task 01, `New-AutomationManagedIdentity.ps1`): creates the user-assigned managed identity of `azure.automation_identity` (type `managed_identity`) in its resource group and the region `azure.location`, with the file-level tags, and reports its client id and principal id; an existing identity is left alone. It creates no role assignment and no resource group, and refuses a `service_principal` (the CI/CD bootstrap creates that). Registry 5.0.23 registers its parameters; no new infrastructure.yml key.
- Azure roles for the Microsoft Entra groups (phase 03 task 02, `Set-EntraGroupRoleAssignments.ps1`): assigns the `roles` of each `identity.entra.groups[]` entry to the group at its `scope` (default: the instance resource group); a role the group holds at exactly that scope is left alone, an unknown role or a missing group is reported, nothing is ever removed. Registry 5.0.22 registers its parameters; no new infrastructure.yml key.
- Hub VPN gateway (phase 04 manual deployment, task 02, `Deploy-VpnGateway.ps1`): creates the Standard zone-redundant public IP address and the route-based gateway of `landing_zone.connectivity.vpn_gateway` in the GatewaySubnet of its network, with BGP on the file ASN. Only AZ SKUs (Microsoft no longer creates the non-AZ ones) and ASNs Azure and IANA do not reserve are accepted; an existing gateway is left alone and a SKU or ASN difference is reported. The site-to-site connections are a later task. Registry 5.0.21 registers its parameters; no new infrastructure.yml key.
- Management group display names (phase 01 task 01, `Set-ManagementGroupDisplayNames.ps1`): sets the display name of each existing group of `landing_zone.management_groups[]` to its `display_name`. A group id cannot be changed in Azure, so only the display name is renamed; a group that already has it is left alone, a missing group is reported. Registry 5.0.20 registers its parameters; no new infrastructure.yml key.
- Microsoft Entra security groups from `identity.entra.groups[]` (phase 03 task 02, `New-EntraSecurityGroups.ps1`): creates one security group (not mail enabled) for each entry, by display name; a group that exists is left alone, a name that two groups share is reported and nothing is created for it. Needs a Microsoft Graph sign-in (`Group.ReadWrite.All`). Registry 5.0.19 registers its parameters; no new infrastructure.yml key.
- The Tier 1 tag policy (phase 04 task 02, `Invoke-AzurePolicyTier1-Orchestrated.ps1`, replaces the scaffold `Invoke-AzurePolicyConfiguration-Orchestrated.ps1`): assigns the built-in policy Require a tag on resources once per tag of `landing_zone.policy.required_tags`, at `landing_zone.policy.management_group` (empty: the tenant root group, `azure.tenant_id`), in audit mode (enforcement mode `DoNotEnforce`, nothing is denied). Assignment names are at most 24 characters (the limit at management group scope), an existing assignment is never changed (a second run creates nothing), `-WhatIf` changes nothing, exit codes 0, 1 and 2. Registry 5.0.18, infrastructure schema 5.6.5: `landing_zone.policy.required_tags` and `landing_zone.policy.management_group`.
- Existing subscriptions under their management groups (phase 01 task 02, `Invoke-SubscriptionMove-Orchestrated.ps1`): makes each `landing_zone.subscriptions[]` entry with an `id` and a `management_group` a direct child of that group; a subscription already there is left alone, a missing group or id is reported, `-WhatIf` changes nothing. Reads only keys that already existed.
- The SBE package is a requirement (registry 5.0.15, infrastructure schema 5.6.4): the OEM package is downloaded and available on a share the automation can read (`hardware.sbe.source_path`, `requirement` required or not_applicable with a reason, optional read account from Key Vault, optional hash and size pins). The pre-cluster verification checks it (SB-001 to SB-006: source, reachable, three files, consistent, family matches the model of every node from the package's own SupportedModels, version validated for the target solution; anything unreadable is Skipped, never Passed). The OS configuration Sbe step reads from the share when the build-time side-load is on and reports the package as available on the share, not side-loaded, when it is off; the side-load (`hardware.sbe.delivery`) stays opt-in and defaults to skip. Phase 06 task 10 prints the files and the exact `Add-SolutionUpdate` commands for the first update.
- Hardware discovery moved to a Redfish core and a vendor adapter: `scripts/common/redfish/AzlRedfishCore.psm1` (read-only GET client, standard DMTF collectors, vendor detection, capability report, bounded parallelism) and `AzlRedfishDell.psm1` (Dell iDRAC adapter). `Invoke-HardwareDiscovery.ps1` picks the adapter by detected vendor (`-Vendor Dell` forces it, `-ThrottleLimit`, `-UseSession`) and writes one schemaVersion 2.0 JSON per node with identity, BMC, system, processors, memory, PCIe and GPUs, network adapters and ports, storage and the BOSS boot device, firmware, BIOS and iDRAC attributes, sensors, an event summary, a capability report and readErrors. Other vendors report `Unsupported vendor in this version`. See `docs/hardware-discovery.md`.
- Hardware discovery fixes from the lab scans: the second LOM port is `Embedded NIC 2` (named from the Port resource, not `Embedded NIC 1 (2)`); the embedded card model is never a generic Dell label such as `Network Adapter View` (it comes from the Dell NIC product name, the PCIe device, or the firmware inventory, else it is empty with a note in the capability report); PCIe devices are read from the Chassis path first (the Systems path is a 404 on iDRAC9) and the report records the path that worked.
- OS configuration joins each node to the domain (step `DomainJoin`, Active Directory designs): after Network, Dns, Time and Hostname, before LocalAdmin; with the LCM user (`domain_join_account` overrides it), a guarded restart with a durable marker, a reconnect and a check (member, domain, secure channel, OU); the dedicated OU is read (exists, Group Policy inheritance blocked, enforced GPO links); a node in another OU is blocked (Microsoft does not support moving computer objects after the deployment); `local_admin_members` are added to the local Administrators; events `DomainJoinPlanned`, `DomainJoinApplying`, `DomainJoined`, `DomainAdminsConfigured`, `DomainJoinFailed`, `NodeRestarting`, `NodeReconnected`. `infrastructure.yml` schema 5.5.0 and rules AZL-050 to AZL-053. See `docs/os-configuration-and-arm-deployment.md#joining-the-domain`.
- Remote management security profiles for the OS configuration run: `scenario.environment_class` (`lab`, `test`, `dev`, `production`, `dmz`; missing means `production`) picks a profile from `config/remoting-profiles.json` (`Resolve-AzlRemotingProfile`): firewall sources for WinRM, RDP and ICMP, HTTP or HTTPS, the TrustedHosts policy of the machine running the automation, the certificate, and whether a one-time bootstrap is allowed. `lab` and `test` are relaxed with the wildcard (sources Any, TrustedHosts `*`, HTTP 5985) and warn; `dev`, `production` and `dmz` take their sources only from the master file. The baseline (AllowUnencrypted false, Basic and CredSSP off, no SkipCACheck or SkipCNCheck, TLS 1.2) holds in every class. Schema 5.6.0 and rules AZL-060 to AZL-068. The RemoteManagement step enables WinRM and opens the firewall itself (rules found by port, on every profile, with the scope of the profile; ICMP, SMB 445 and WS-Man 5985 between the nodes in every class) as a guarded change (snapshot, stage, confirm, commit or revert). `bootstrap_transport` `none | arc | smb | auto` opens WinRM once on a node whose firewall keeps the orchestrator out (smb: sc.exe from a Windows orchestrator; arc: Run Command with a capped wait); production and dmz need `-ApprovedBootstrap`. See `docs/os-configuration-and-arm-deployment.md`, *Remote management security profiles*.

- `Invoke-AzureLocalOsConfiguration.ps1` and `AzlOsConfigurationRun.psm1`: the whole OS configuration phase for a whole instance in ONE run (`-Mode Plan` or `Apply`). It merges every `*.ztp-handoff.json` under `-HandoffPath`, works out the method per node (a ZTP-provisioned machine over Arc Run Command with only the steps ZTP left undone, or an ISO-installed machine over WinRM with the local administrator from the vault, the computer name, the OS check and Arc registration), plans for all nodes, applies node by node (a failed node does not stop the others), verifies with a Plan pass (a node is converged only when that pass finds nothing left), and writes `report.json`, `summary.md`, `plan-report.json`, `wipe-list.txt` and exit codes 0/1/2. It calls `Set-AzureLocalNodeConfiguration.ps1` per node, so it uses the SBE delivery route of `hardware.sbe.delivery`; for `winrm_copy` on a node reached over Arc it passes the local administrator for the copy, and a node whose plan says the package is NOT DELIVERED gets a warning in the report. GitHub Actions and GitLab CI pipelines run it unchanged: `pipelines/github/os-configuration.yml`, `pipelines/gitlab/os-configuration.gitlab-ci.yml`.
- `infrastructure.yml` schema 5.4.3 and rule AZL-031: `os_configuration.clear_storage` (default `false`). `true` lets the OS configuration run wipe leftover storage pools, virtual disks and the data on non-boot, non-system local disks in Apply mode; Plan prints and writes the wipe list per node (the pipeline's approval gate shows it); SAN (Fibre Channel, iSCSI), USB, boot and system disks are never touched; AZL-031 warns on a SAN design.
- `Set-AzureLocalNodeConfiguration.ps1`: `-NodeAddress` (the address to open a WinRM session to, also for the `winrm_copy` of the SBE package), `-RetryTries` and `-RetryDelaySeconds` (a node script whose Arc run command ends in state `Unknown` is tried again with a growing pause; after the last try the node is read again and convergence is decided by what is found), `hostname` and `osVersion` per node in the report, `Set-AzlNodeRetryPolicy`, and `Invoke-AzlNodeScript -Tries`. A restart that ends in `Unknown` is not a failure.- A draw.io diagram of the OS configuration flow, `docs/diagrams/os-configuration-flow.drawio` with its exported PNG, embedded in `docs/os-configuration-and-arm-deployment.md`: the ZTP handoff and `infrastructure.yml` in, the three management address modes, each step in run order (marked skip-if-correct, read only or opt in), the SBE delivery routes, and the exit to ARM Validate and Deploy.

- `infrastructure.yml` schema 5.4.2 and rule AZL-030: `hardware.sbe.delivery` (`winrm_copy`, `node_pull` or `skip`, default `skip`) and `hardware.sbe.node_pull_url` choose how the Dell SBE package reaches the nodes' `C:\SBE` during OS configuration. `node_pull`: each node downloads the files from a read-only HTTPS or UNC location and the SHA-256 is checked on the node. `winrm_copy`: copied over a WinRM session (to a `.part` file, checked, renamed) from the host that runs the script, beside the Arc transport for the other steps. `skip`: the Sbe step reports "NOT DELIVERED" and nothing else is affected. The Sbe step now runs last, so a delivery that fails never stops the other steps.
- `infrastructure.yml` schema 5.4.1: `provisioning.simplified.timeouts.adapters_minutes` (default 10). azurelocal-ztp's Network stage waits that long for an edge machine to report its network adapters before it judges the management port; a machine whose management port never shows up in the list within that time is not verified in any mode (a Warning, never a success state), and the Handoff stage reads the adapters again. 0 reads once and does not wait.
- Dell hardware discovery, the first stage of the flow (before azurelocal-ztp and the OS configuration), rewritten for `infrastructure.yml` schema 5 and PowerShell 7: `Invoke-HardwareDiscovery.ps1` (Phase 01 Task 02) reads every `nodes[].bmc.ip_address` through Redfish (read only) and writes `<ServiceTag>.json`, `discovery-summary.json` and a reviewable `infrastructure.discovered.yml` (service tag as `serial_number`, one `network_adapters[]` entry per port with its MAC, slot and model, a suggested management port with the reason, the BOSS card and whether its virtual disk exists). `Update-InfrastructureYml-FromDiscovery.ps1` previews, and with `-Apply` edits only the serial and MAC lines (backup, confirmation, comments kept). `Get-DellServerInventory-FromiDRAC.ps1` keeps the full inventory per service tag, `Get-HardwareDiscovery-Standalone.ps1` is the single-file version, and `Enable-IdracVnc.ps1` sets the iDRAC VNC server (`-WhatIf`). New modules `AzlDellRedfish.psm1` and `AzlInfrastructureEdit.psm1`; credentials from `-Credential`, Key Vault references in the file, or a prompt; no plain-text password is read from a file. Dell endpoints reference moved to `config/oem/dell-endpoints.md`. Pester tests with a fake iDRAC in `tests/discovery`. Removed the unused `-Solution` set, the PowerShell 5.1 certificate code and the `compute.cluster_nodes` / `macs.*` paths of the earlier scripts.
